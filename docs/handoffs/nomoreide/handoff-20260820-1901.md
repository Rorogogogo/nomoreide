## What this session added (and why it matters to implementation)

An audit of `src-tauri` produced numbers that changed the plan's sequencing. Do not re-derive them:

- **19,367 lines of Rust already exist.** `src-tauri/src/core/` (19 files, 6,700 lines) has **zero** Tauri references — it is already a standalone runtime library and moves into `crates/nomoreide-core` as a file move, not a port.
- `src-tauri/src/commands/` (11,700 lines) is thin-coupled: ~143 of ~180 Tauri references are the single `State<AppState>` parameter per `#[tauri::command]`. Bodies are ordinary Rust.
- `src-tauri/src/core/config.rs:498` already resolves the same `~/.config/nomoreide/config.json` that `src/core/config-store.ts:408` writes — the Phase 1 config-compatibility gate is largely pre-satisfied.
- The one genuinely Tauri-shaped seam is event emission: ~22 `app.emit(...)` sites (~13 `terminal.rs`, ~5 `agent_chat.rs`, ~4 `onboard.rs`) plus `AppHandle` in `open_in_terminal`/`reclaim_to_dock`.
- ~67 TS core modules (~12,400 lines) have no Rust counterpart at all. 18 modules exist on both sides and have **drifted in both directions** (`process-manager` 508 Rust vs 891 TS; `vercel-oauth` 460 Rust vs 86 TS).

## Key decisions & constraints

- **Phase 1 lifts `core/` out of `src-tauri` immediately.** The original plan deferred Tauri convergence to Phase 6, which would have meant three concurrent implementations (TS, Tauri-owned, daemon-owned) for five phases. This reordering is the single most important change made.
- **`nomoreide-client` must not depend on `nomoreide-core`.** This is the compile-time guard against today's bug where `src-tauri/src/lib.rs:22` builds its own `ConfigStore`/`LogStore`/`ProcessManager` and neither app sees the other's services. It is a Phase 1 exit-gate item.
- **`nomoreide-client` = daemon client, not web client.** Different from `apps/dashboard`. Rename to `nomoreide-daemon-client` if review finds it confusing.
- **Counterpart ≠ parity.** Every ported module is judged by the Phase 0 parity harness, never by "Rust already has one."
- **`src/` is deliberately NOT renamed.** 648 tracked files, 236 test files importing `../src/...`, all deleted at Phase 8. It becomes unambiguous once the dashboard moves out.

## Next slice — PR 2 (dashboard extraction)

Move `src/web/client` → `apps/dashboard`. Behaviour-neutral, but it touches release-critical paths:

1. Split `package.json` — ~30 of 41 runtime deps (react, framer-motion, `@xterm/*`, codemirror, tailwind, vite …) are used **only** under the client and were verified to appear nowhere else in `src/`. They currently ship to every `npm i -g nomoreide`.
2. Split root `vite.config.ts` into `apps/dashboard/vite.config.ts` + a root `vitest.config.ts` (the root file currently does both jobs).
3. Keep the `dist/web/client` **output path identical** — `src/web/static-assets.ts` and the daemon both resolve it.
4. Update `.github/workflows/ci.yml:48` (client typecheck path).
5. `scripts/sync-version.mjs` must learn any moved path in the same PR, or `deploy.yml` breaks at release time rather than in CI.

Gate: `npm run build`, `npm test`, `npm run lint`, `npx tsc -p <client tsconfig> --noEmit`, and a daemon actually serving the built client.
