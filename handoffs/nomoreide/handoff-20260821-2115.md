## What was fixed

### 1. Windows starts (`process_manager.rs`, `runtime_registry.rs`, `tests/http_api.rs`)

The journal is now explicitly Unix-only via `RUNTIME_JOURNAL_SUPPORTED` and a `ProcessManager::journal()` accessor that gates every journal use — recording, reconciliation, supervisor cleanup, and the no-supervisor stop path. Windows already gets the guarantee the journal exists to provide: children are assigned to a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so the kernel tears the tree down when the owner's last handle closes, crash included. Consequences:

- registered starts no longer wait on an identity Windows cannot report, so they no longer time out and kill the child;
- reconciliation is skipped instead of rejecting every record, so a stale/foreign registry file can no longer stop the next daemon from publishing;
- `RuntimeRegistry::record` carries `#[cfg_attr(not(unix), allow(dead_code))]`;
- `corrupt_native_registry_fails_before_daemon_publication` is now `#[cfg(unix)]`.

Windows stop still fails closed when a generation has no supervisor and unconfirmed cleanup — it uses `journal()`, so it can no longer "confirm" cleanup by removing from a registry it never wrote.

### 2. Stop after config drift (`crates/nomoreide-daemon/src/runtime.rs`)

`DaemonRuntime::stop_service` only requires a current registered-local definition when `ProcessManager` does *not* already own the name. A running service stays stoppable after its definition is edited, removed, or made unparseable; unmanaged names still get `SERVICE_NOT_FOUND` / `CONFIG_LOAD_FAILED`.

### 3. Registry cleanup retry (`process_manager.rs`)

`stop_service_locked` no longer returns `Ok` for a `Stopped` generation whose `cleanup_confirmed` is false. It falls through, re-checks that the process group is gone, retries the registry removal, and only marks confirmed on success. An unconfirmed generation therefore keeps blocking starts and keeps `shutdown_all` (and so daemon shutdown) failing until the removal actually lands.

### 4. Crash-safe launch handshake (`process_manager.rs`, `port_utils.rs`)

`register_child` was split into `launch` + `register_child`, and the Unix launch now parks the child before `exec`:

- `LaunchHandshake` creates two close-on-exec pipes (`pipe2` on Linux, `pipe`+`fcntl` elsewhere).
- `pre_exec` (async-signal-safe only) closes the owner's ends, writes `pid`+`pgid` to the announce pipe, then blocks reading the release pipe. EOF there means the owner died, and the child `_exit`s with 126 **without ever executing the service**.
- `std`'s spawn blocks until the child execs, so `Command::spawn` runs in `spawn_blocking` while the runtime task reads the announcement, journals the record, and only then writes the release byte.
- Only the announce step races the spawn (so a child that dies early fails fast); once announced the child is parked, so the journal write is never cancelled mid-write.
- The launch gate serialises handshakes so a concurrent `fork` cannot inherit another launch's release pipe.
- Identity now comes from the kernel (`port_utils::process_start_token`, no `ps` fork) and is captured *before* `exec`. The start token is stamped at fork and survives `exec`, so it is stable across the whole handshake.
- Because the observed command line changes at `exec`, `RuntimeRecord.command` is now a diagnostic label built from the service definition (kind + command + args, never env values), and reconciliation verifies `pid` + `pgid` + `uid` + `start_token` only. `pid` plus the kernel start token is already the exact identity of one process instance.
- `abort_at_launch_stage` is an env-gated fault-injection point (`NOMOREIDE_UNSAFE_TEST_ABORT_AT_LAUNCH_STAGE`, stages `announced` and `journaled`), inert unless the variable names the exact stage.

## New tests

- `crates/nomoreide-core/tests/launch_crash.rs` — black box: a real owner subprocess is aborted inside each half of the launch window; asserts the owner died by `SIGABRT`, the service never executed (its marker file never appears), and that the post-journal case leaves exactly one record the next owner reclaims to a clean journal and a dead group.
- `process_manager.rs`: `journaled_launch_is_durable_before_the_service_executes`, `a_launch_that_cannot_be_journaled_never_executes_the_service`, `a_command_that_cannot_execute_reports_its_error_and_leaves_no_record`, `unconfirmed_registry_cleanup_is_retried_until_it_succeeds` (fail → retry → shutdown refused → succeed → startable again).
- `tests/http_api.rs`: `managed_services_stay_stoppable_after_their_definition_drifts` (definition removed, then config unparseable).

## Constraints still in force

- Concrete daemon-local coordinator; core is not a global actor.
- Start stays registered-local-only and uses config definitions, never request-supplied commands/argv/env.
- Stop stays a remediation capability after config drift or cleanup failure.
- Registry stays private, versioned, Unix-only, and separate from TypeScript `~/.nomoreide/runtime.json`: `<state-dir>/native/runtime-v1.json`.
- Recovery completes before daemon state/credential publication.
- Cleanup failure retains listener, health, credential, and ownership; starts blocked, remedial stops and shutdown retries possible.
- Owner pinning/revalidation before bearer transmission, loopback-only binding, request timeouts, argv execution, exact process identity checks, and MCP stdout purity all preserved.
- Tauri still owns its existing runtime (`ProcessManager::new`, no journal, unchanged behaviour). Phase 2 is not complete.
