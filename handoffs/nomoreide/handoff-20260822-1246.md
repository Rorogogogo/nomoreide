## What this session did

### The Phase 2 exit gate now exists (`a1fd02e`)

`npm run mcp:runtime-parity -- ./target/debug/nomoreide`
(`scripts/check-mcp-runtime-parity.ts` + `test/support/runtime-parity.ts` +
`test/fixtures/mcp-runtime-parity-v1.json`).

Each runtime gets a private throwaway home, an identical service config, and one
ordered walk of **55 MCP calls** across every state a service reaches (running,
exited, stopped-after-running, never-started, restarted, bundled, refused) and
all three kinds. `--dump` prints both payloads per step.

It compares payloads instead of reading either implementation, and normalizes
only what cannot repeat between two equivalent runs: pids, ports, wall-clock
times, each runtime's own paths. States, exit codes, signal names, and message
text are compared verbatim.

Hermetic: `ssh` and `docker` are stubs planted per workspace. **A stub needs
`SHELL` as well as `PATH`** — `service_path()` asks the login shell what PATH to
hand a service and appends the inherited one last, so a stub reachable only via
`PATH` loses to a real `/usr/local/bin/docker`.

**Verified the gate actually bites**: injected a wording regression into
`errors.rs`, watched it fail 2 steps (including reporting that a *pinned*
divergence had changed), then reverted.

### Four accepted divergences — decided by the user, do not relitigate

The user chose **"record as accepted divergences"** over changing either
runtime. Implemented as narrow reconcilers (not skipped steps), so every other
field in those steps is still compared. The two statable ones are pinned on
**both** sides, so the gate fails if either runtime changes.

| # | Difference | Treatment |
| --- | --- | --- |
| D1 | A stop finding no live child makes the reference discard the exitCode/signal/pid/url it just reported; native carries them forward | Reconciled: only what the reference kept is compared |
| D2 | Reference *invents* a runtime entry + timeline event for a stop of a never-registered name, and it persists in later reads; native refuses | **Pinned** at `error/stop-unregistered` |
| D3 | Reference records every stop twice (exit watcher + `stopService`, the latter with no `data`) | Reconciled: data-less twin dropped |
| D4 | ssh env assignments are file-ordered in the reference, sorted natively | **Pinned** at `logs/ssh-argv`; sorted elsewhere |

In all four the native behaviour is the better one. D4 was invisible until a
second env var was added to the fixture in deliberately non-alphabetical order.

Two further differences are **races present in both runtimes, not divergences**:
a service's URL is parsed out of stdout asynchronously (so a *start* may return
before or after it lands — `volatile: ["url"]` on start steps, the following
`status` step compares it settled), and the stdout/stderr readers race so events
for *different* services interleave either way (order within one service is
deterministic and still compared).

### One real bug the gate found (`4b933d7`)

Start/restart/stop for an unregistered name answered `Service is not
registered.` where the reference answers `Service "api" is not registered.` —
the agent could not tell which name it got wrong. Both not-found variants are
now tuple variants carrying the name; every construction site already had it in
scope.

### CI (`8eeff9f`)

Added to the existing `desktop-check` job (already has Node, `npm ci`, a built
client, warm Rust cache): an explicit `cargo build --workspace` then the parity
run. The build is explicit rather than relying on `cargo test` building the
binary incidentally.

Also raised the harness's daemon-startup wait from 6s to a **60s deadline** —
the reference boots through tsx, compiling on the fly, and a cold CI runner
would have timed out and read as a parity failure.

**The gate has never run in CI yet** (nothing pushed). If it proves flaky under
CI load, that surfaces on the first PR.

## Next task: split `git_manager.rs` (recommended first Phase 3 slice)

Recon done this session:

- `crates/nomoreide-core/src/git_manager.rs` is **857 lines / 28 public
  methods**, inherited from Tauri: `status`, `diff`, `file_diff`, `log`/`graph`,
  `branches`, `stage`/`unstage`, `commit`, `worktrees`, `create_worktree`,
  `remove_worktree`, `prune_worktrees`, `fetch`, `read_file`, `write_file`,
  `push_with_credential`, `pull`, `merge`, `rebase`, `create_branch`,
  `delete_branch`, `switch_branch`, …
- Against 19 git MCP tools on the TS side, Phase 3's git slice is mostly
  **wiring** (daemon routes + MCP adapters), not a port from scratch.

**The problem:** TypeScript splits git deliberately and CLAUDE.md calls the
split load-bearing, but the Rust module collapses it —

| `src/core/git-manager.ts` (agent-reachable) | `src/core/git-actions.ts` (guarded, 207 lines) |
| --- | --- |
| status, diff, stagedDiff, log, graph, branches, stage, unstage, commit, createBranch, deleteBranch, switchBranch, fetch, readTrackedFile, writeTrackedFile | **push, pull, merge, rebase**, checkoutDefaultAndPull + credential handling |

Note "read-safe" here means *no network, no history-integration* — it does
include stage/commit/branch ops. `git-actions.ts` also holds the credential
helper that keeps a token out of `argv` (`CREDENTIAL_HELPER`, and the empty
`credential.helper=` that resets the inherited chain so the machine keychain
cannot push as the wrong account) — port that behaviour exactly.

**Recommended slice:** split into a read-safe module and a guarded
`git_actions.rs`, with `nomoreide-mcp` linking only the read-safe half, so "MCP
cannot push" is a **compile error** — the same structural trick Phase 1 used for
"the daemon client cannot reach core" (gated by `npm run
rust:dependency-check`). Self-contained, no new surface, sets the shape for the
other 35 tools.

Then: repo registration/selection → status/diff/log reads → worktrees → GitHub
auth + API → snapshots/onboarding.

Existing Rust in the domain: `git_manager.rs` (857), `git_identity.rs` (421),
`github_auth.rs` (252). No worktree/snapshot/onboard module yet.

`RuntimeHarness`, the normalization, and the pin/reconcile machinery in

fixture are service-specific. Phase 3's exit gate (clean/dirty repos, detached

second fixture + plan against fixture *repos*. Build it incrementally alongside
each slice rather than all at the end.

## Known non-issues — do not re-investigate

- Metrics are **not** an MCP gap (`processTree` only reaches the dashboard).
  Saved as the `metrics-are-not-on-the-mcp-surface` memory.
- The `services` map is sorted by name natively, insertion-ordered in the
  reference. Deliberate and documented.
- Native tools need a reachable daemon where the reference falls back; a
  malformed `tools/call` `params` answers `-32602` vs the reference's `-32603`.
- `serde_json` sorts object keys, so key *order* can only be asserted against
  rendered text, not a parsed object.
- `nomoreide-tauri`'s `commands::terminal::tests::close_all_kills_and_reaps_*`
  is flaky under parallel load; passes in isolation.
- `process_exists` (`kill(pid, 0)`) reports zombies as alive.
- Windows cross-check emits only pre-existing `filesystem.rs` `options`
  warnings.

## Constraints still in force

- Concrete daemon-local coordinator; core is not a global actor.
- Start is registered-definition-only. Stop is a remediation capability. Reads
  (logs, timeline) are deliberately more permissive than starts; a *context
  packet* is not such a read — an unregistered name is a refusal.
- Journal stays private, versioned, Unix-only, at
  `<state-dir>/native/runtime-v1.json`. Compose never touches it.
- Owner pinning before bearer transmission, loopback-only binding, request
  timeouts, argv execution, exact process identity checks, MCP stdout purity.
- Tauri owns its own runtime (`ProcessManager::new`, no journal, no timeline).
- Workspace MSRV is **1.77.2** — clippy's `incompatible_msrv` rejects
  `is_none_or`. Use `map_or`.
- Bundle mutations use a 120s client timeout; single-service 10s.
