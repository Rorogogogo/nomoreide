## The open divergence — measured, not suspected

`nomoreide_status` (and the status every start/stop/restart/bundle tool returns)
reports **fewer fields than the reference**. Diffed against a live reference
daemon with one running service:

```
reference                       native
{ "name": "quiet",              { "name": "quiet",
  "state": "running",             "state": "running",
  "kind": "local",                "pid": <PID> }
  "pid": <PID>,
  "startedAt": "<TS>" }
```

This is **pre-existing**, from `eaf63db`/`54a757e` — not introduced by this
session. `crates/nomoreide-mcp/src/tools.rs`'s `ServiceStatusView` was written to
a field set that a comment calls "the status shape the reference implementation
returns", and that comment is wrong.

The full reference shape, read back from the running reference in every state,
is one declared key order with absent fields skipped:

```
name, state, kind, pid, startedAt, url, exitedAt, exitCode, signal
```

- running, url detected: `name, state, kind, pid, startedAt, url`
- exited: `… startedAt, exitedAt, exitCode, signal` (no url)
- stopped after running: all nine
- stopped, never ran: `{ name, state }` and nothing else — which
  `stopped_status` already produces correctly

`exitCode` and `signal` are an explicit pair once a process has terminated: one
of the two is `null` rather than absent (`"exitCode": 3, "signal": null`, or
`"exitCode": null, "signal": "SIGTERM"`).

**What closing it needs**, in rough order:

- `startedAt` — **already done** this session; on `ManagedProcess`,
  `ServiceStatus`, and the wire. Only the view omits it.
- `kind` — store it on `ManagedProcess` at launch the way the reference does,
  rather than joining config at read time; a service dropped from config after it
  started still has a kind.
- `exitedAt` + `signal` — `finish_generation` in `process_manager.rs` is the one
  place a terminal state settles, and it already receives everything needed: it
  takes `exit_code: Option<i32>` today where every caller has a whole
  `Termination { exit_code, signal }`. Widen that parameter and stamp
  `exited_at` there.
- Signal **names**: the reference reports `"SIGTERM"`, `Termination.signal` is an
  `i32`. Needs a number→name mapping.
- `ServiceStatusView` then declares the nine keys in the order above.

This changes a shipped wire shape, which is why it was left for an explicit
decision rather than folded into a tool slice.

`host` (ssh) and `containerId` (compose) sit in that same shape but can never
appear natively — the runtime refuses both kinds with `UnsupportedServiceKind`.
`processTree` and `inspector` likewise have no native sampler.

## What this session did

### `nomoreide_service_context` + `nomoreide_service_health` (`fa43690`)

Both join the registered definition (local config) with the runtime reading (the
daemon). New `core/agent_context.rs` holds the prose packet; `core/service_health.rs`
was **replaced** — the module there was dead code that asked the log store's
severity classifier whether a line was an error. The reference runs a *wider*
substring scan for this purpose (`/error|failed|exception|panic|fatal|traceback|exit status/i`),
so `0 errors` **does** count here even though the timeline classifier deliberately
keeps it off the timeline. Two different questions, two different pattern widths —
do not re-unify them.

Both take borrowed snapshot types core defines itself rather than daemon-client
wire types, because `npm run rust:dependency-check` enforces that core sits below
the client crate. Nothing needs parsing: the reference compares timestamps as
strings, and ISO-8601 UTC sorts lexicographically.

`startedAt` was added to the runtime for this: the log buffer outlives the
process, so without it a just-repaired service goes on reporting the error that
prompted the repair. It survives the exit it belongs to on purpose.

The reference's high-memory branch (>1 GB RSS → warning) has no native
counterpart and is absent rather than stubbed; `processTree` never appears.

### `nomoreide_register_service` + `nomoreide_register_bundle` (`071e849`)

Registration writes config and never touches the runtime, so `execute` now serves
it **before** discovering a daemon. Requiring one would invert the order the two
things actually happen in.

Two gates, both the reference's. `protocol/contracts.rs` asks whether each field
is well-formed; `tools/registration.rs` asks whether the fields together describe
a service. `{ "name": "api" }` is eleven valid fields and no service.

The second gate's refusal is the reference's own validator report, reproduced —
including which of the three readings gets quoted. A reading that recognised the
service and merely rejected a value is reported **alone**; only when no reading
applies does the `invalid_union` dump list all three. That rule is zod's
dirty-vs-aborted distinction and it is load-bearing for parity.

Two fidelity fixes fell out:

- **`public_value()` sorted every key.** It returned a `serde_json::Value`, whose
  `Map` is a `BTreeMap` without the `preserve_order` feature, so the struct's
  declared field order never survived. `Config::public_view()` now serializes
  without that round trip and `public_value()` is written in terms of it.
  **Anything rendering the public config for comparison must use `public_view`.**
- `PublicServiceDef`'s declared order was wrong against the reference anyway, as
  was `PublicConfig`'s optional tail. Both are now the reference's.

### Contracts extraction (`ab9b893`)

Pure move of `ArgumentContract` and its validators into
`crates/nomoreide-mcp/src/protocol/contracts.rs`, ahead of registration's eleven
fields. Session tests stayed in `protocol.rs` — what they exercise is the
boundary that turns a rejection into a `-32602` frame.

## Two bugs this session caught, both worth remembering

- **An inverted refinement passed every test that existed.**
  `entries.keys().all(is_env_name).then_some(())?` returns `Some` when everything
  is *valid*, so a good `env` was rejected and a bad one accepted. Only the
  reference diff caught it. `.any(|k| !ok(k)).then(…)` is the correct shape.
- **A `python3` string-replace patch that silently does not apply.** Twice a
  replacement targeted text that `cargo fmt` had already reflowed; the script
  printed `ok` and changed nothing, and the fix appeared to fail for a different
  reason. Re-`grep` after any scripted edit to a file `cargo fmt` has touched, or
  use the Edit tool, which fails loudly.

## How the argument contracts are established

Do **not** derive wording from zod source. Launch the reference and diff frames.
Scratch probes used this session (in the session scratchpad, disposable):

- `probe.mts` — one reference MCP process, many `tools/call` frames, no daemon.
- `probe2.mts` — reference daemon + reference MCP, for anything runtime-shaped.
- `parity.mts` — reference and native side by side against identical fixture
  homes, normalizing timestamps/pids/paths, comparing tool **payloads** (frame
  key order differs between the two runtimes and is not meaningful).

Things this turned up that reading would have got wrong:

- `kind` has two wordings: `Invalid enum value. Expected 'local' | … , received 'z'`
  for a string, `Expected 'local' | … , received number` for anything else.
- An argv member may be the empty string; a bundle member may not.
- A `kind` that was *sent* is quoted back as `received` ahead of `code`; a `kind`
  that was never sent leaves the key out entirely (JS drops `undefined`).
- A missing field's issue is `{code, expected, received, path, message}` with
  `received: "undefined"` as a **string**.

## Known non-issues — do not re-investigate

- Native tools need a reachable daemon where the reference falls back; a
  malformed `tools/call` `params` answers `-32602` where the reference answers
  `-32603`. Both reproduce against already-shipped tools.
- Timeline events written in the **same millisecond** by the stdout and stderr
  readers can interleave differently. Two independent readers race in both
  runtimes; 4 of 5 parity runs matched exactly, and the fifth differed only in
  that order.
- `serde_json` sorts object keys, so two bad `env` entries are reported
  alphabetically rather than in the order they were written. Documented in
  `contracts.rs`.
- `nomoreide-tauri`'s `commands::terminal::tests::close_all_kills_and_reaps_every_session_and_descendant`
  is flaky under parallel load — it failed once and passed once on *identical*
  code this session, and passes in isolation. Same family as
  `close_kills_sighup_resistant_child_and_descendant_process_group`. Nothing to
  do with any of this work.
- `process_exists` (`kill(pid, 0)`) reports **zombies as alive**. Safe for
  daemon-owned children, not as a general liveness assertion.

## Constraints still in force

- Concrete daemon-local coordinator; core is not a global actor.
- Start stays registered-local-only, from config definitions only. Stop is a
  remediation capability. **Reads (logs, timeline) are deliberately more
  permissive than starts** — an unregistered name reads back empty. A *context
  packet* is not a read in that sense: an unregistered name is a refusal, because
  the packet is built around a definition.
- Journal stays private, versioned, Unix-only, at
  `<state-dir>/native/runtime-v1.json`.
- Owner pinning before bearer transmission, loopback-only binding, request
  timeouts, argv execution, exact process identity checks, MCP stdout purity.
- Tauri owns its own runtime (`ProcessManager::new`, no journal, no timeline) but
  shares `core::bundle` ordering.
- Workspace MSRV is **1.77.2** — clippy's `incompatible_msrv` rejects `is_none_or`
  and friends. Use `map_or`.
- Bundle mutations use a 120s client timeout; single-service 10s.
